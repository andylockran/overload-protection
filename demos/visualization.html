How It Works

Event Loop Monitoring: The overload-protection library uses loopbench to measure the delay between event loop ticks. When the event loop is busy with CPU-intensive tasks, the delay increases.

Threshold Detection: When the event loop delay exceeds maxEventLoopDelay (default 42ms), the middleware detects overload and starts rejecting requests with 503 (Service Unavailable).

Load Shedding: By rejecting requests early, the server protects itself from cascading failures. Rejected requests can retry later (via Retry-After header), allowing the server to recover.

Memory Monitoring: The library also monitors heap usage and RSS memory, providing comprehensive protection against resource exhaustion.

🎯 What to Watch For

  • Event Loop Speed: The rotating indicator spins quickly under normal load, slows down dramatically when overloaded
  • Request Colors: Blue circles = accepted (200 OK), Red circles = rejected (503)
  • Green Pulses: Show the sampling interval (every 5ms by default)
  • Delay Threshold: Watch the delay fluctuate above and below 42ms threshold when you click "Simulate Fluctuating Load"
  • Recovery Cycles: Observe how the system automatically recovers when delay drops below threshold

📊 Configuration Options

  • maxEventLoopDelay: 42ms (default) - threshold for event loop lag detection
  • maxHeapUsedBytes: 0 (disabled) - can monitor heap memory usage
  • maxRssBytes: 0 (disabled) - can monitor RSS memory usage
  • sampleInterval: 5ms - how often to check event loop delay
  • clientRetrySecs: 1s - tells clients when to retry via Retry-After header

🔄 Request Lifecycle

  1. Arrival: Request appears in "Incoming Requests" section
  2. Overload Check: Middleware checks if profiler.overload === true
  3. Decision:
    • If overloaded: Immediate 503 response, request moves directly to responses (red)
    • If not overloaded: Request enters event loop for processing (blue)
  4. Processing: Request is processed in the event loop (adds to delay if heavy)
  5. Response: Completed request moves to "Responses" section
  6. Cleanup: Response fades out after 1 second

⚡ Why This Matters

Without overload protection, a surge of requests would queue up, causing ALL requests to experience extreme delays. The event loop would become blocked, making the entire server unresponsive. By rejecting excess requests early (fail-fast), the server maintains responsiveness for requests it CAN handle, preventing cascading failures.

This is especially critical for microservices where one overloaded service can bring down an entire system through retry storms and resource exhaustion.
